# OpenCCTVMiD

Local control for the **Xiaomi Dafang 1080p PTZ camera** (`isa.camera.df3`),
speaking the miIO protocol directly over UDP 54321. No cloud, no Mi Home, no
vendor servers.

React Native (Expo prebuild) + TypeScript. Built against firmware
`5.5.1_1025`.

---

## Read this first

Your camera runs **stock firmware**, and that decides what's possible.

| | Stock firmware | Dafang-Hacks custom firmware |
|---|---|---|
| Live video | P2P only — **not** reachable | RTSP + MJPEG + snapshot URL |
| PTZ motors | unknown, must be probed | direct, documented |
| Toggles (night mode, LED, motion) | partly, via miIO | all of them |
| Install risk | none | needs an SD-card flash |

**Live video is the honest gap.** Stock firmware streams over Xiaomi's
proprietary TUTK P2P channel, not RTSP. `videoP2Proxy` converts P2P to RTSP but
its author only claims support for `lumi.camera.aq1`, and people who tried it
against `isa.camera.df3` reported it failing. This app does control, not video.
Keep Mi Home for the picture.

**PTZ is an open question, and the app is built around that.** Xiaomi never
published the method list for this model; python-miio has no driver for it and
the request to add one was never resolved. So rather than ship buttons that
pretend to work, the app **probes**: it calls each candidate method once and
reads the reply.

That reply is informative:

| Reply | Meaning |
|---|---|
| `unsupported_method` / `-32601` | the name is wrong, move on |
| `invalid params` / `-32602` | **the method is real** — only the arguments were off |
| a result | it works |

The Control tab then shows only what your camera actually confirmed. If PTZ
comes back empty, that's a real answer too: this firmware keeps motor control on
the P2P channel, and custom firmware is the only route.

## Getting the token

The token is the camera's local password: 16 bytes, never transmitted, used to
derive the AES key (`key = md5(token)`, `iv = md5(key + token)`). Mi Home holds
it.

1. **Easiest** — run
   [Xiaomi-cloud-tokens-extractor](https://github.com/PiotrMachowski/Xiaomi-cloud-tokens-extractor)
   on a PC and sign in with your Mi account.
2. **Offline** — pull `/data/data/com.xiaomi.smarthome/databases/miio2.db` from
   a rooted phone or an Android emulator running Mi Home.
3. **Sometimes free** — the app's *Scan the network* button broadcasts a hello
   packet; some firmware leaks the token in the reply. Yours probably won't.

Resetting the camera or re-adding it in Mi Home **changes the token**. A token
is full control of the device — treat it like a password.

## The Python tools

The same protocol, runnable on any PC — or on the phone itself under Termux.
Faster to iterate with than an app build, and the probe results are identical.

```bash
cd tools
pip install cryptography

python3 verify.py                                    # 39 self-tests, no camera
python3 probe.py --discover
python3 probe.py --ip 192.168.1.11 --token <32 hex> --out findings.json
python3 probe.py --ip 192.168.1.11 --token <32 hex> --call set_video '["on"]'
```

`verify.py` stands up a fake camera on localhost and checks the packet layout,
the checksum, the AES round-trip, the stale-reply filter and the wrong-token
path. Run it before you suspect the network.

### The two implementations are checked against each other

`__tests__/vectors.json` holds packets and ciphertexts generated by the Python
client — the one verified against a simulated device. The TypeScript suite
asserts byte-for-byte equality against them, so the port isn't merely
self-consistent; it agrees with the implementation known to produce valid
frames.

This caught a real divergence: Python's `json.dumps` emits `{"id": 7, ...}`
with spaces, JavaScript's `JSON.stringify` emits `{"id":7,...}` without. Both
are valid JSON, but the packets differed. Python is now pinned to compact
separators.

## What this camera actually answers

Measured against real hardware: `isa.camera.df3`, firmware `5.5.1_1025`,
device id `59549501`, on 2026-11-08. Everything below is observed, not
inferred from the spec.

**Methods that reply**

| Method | Result |
|---|---|
| `miIO.info` | works — model and firmware |
| `get_prop` | works |
| `set_cruise` | returns `"ok"` |
| `set_track` | returns `"ok"` |

Every other method in `commands.ts` — all the PTZ candidates, `set_video`,
`set_power`, `set_night_mode`, `set_flip`, the motion-detection family,
storage — returns **nothing at all**. Not `unsupported_method`: silence. A
conforming miIO device answers an unknown method with an error, so this
firmware's behaviour means "no reply" cannot be distinguished from a dropped
packet without the handshake as a control.

**Properties that return a value**

| Property | Value seen |
|---|---|
| `power` | `on` |
| `night_mode` | `0` |
| `sdcard_status` | `0` |

`light`, `flip`, `watermark` and `motion_record` are recognised but return
null. `cruise` and `track` return nothing at all — they are writable but not
readable.

**`get_prop` drops unknown names instead of padding the reply.** Asking for
`["cruise","track","power","night_mode"]` returns `["on","0"]` — two values
for four names, which are `power` and `night_mode`. Any code that zips the
request against the response will mis-assign every value after the first
gap. Query one property per call, or match by elimination.

**`set_cruise("on")` does not move the camera.** It returns `"ok"` and the
motors stay still. The acknowledgement means the firmware parsed the write,
not that anything acted on it.

**MIoT is a dead end locally.** `get_properties` is accepted for any
siid/piid and returns `[]` every time — including siid 2 / piid 1, the one
property the published spec does list. The RPC envelope succeeds while the
payload is empty, so judging a call by whether it replied marked thirteen
meaningless grid calls as working. `action` returns nothing at all for every
siid/aiid tried.

A reply is not a result. `isEmptyResult` in `src/miio/result.ts` encodes
that, with the observed replies as its test cases.

### The conclusion

PTZ is not reachable over miIO on this firmware. Pan/tilt rides the same
proprietary P2P channel as the video, which is why the Mi Home plugin can
drive the motors and a local client cannot. The published MIoT spec, which
lists only a power switch and P2P stream start/stop, understates the surface
slightly — `get_prop`, `set_cruise` and `set_track` all answer — but not in
any way that reaches the motors.

Custom firmware remains the only route to local PTZ and RTSP, and the
install flashes the camera's internal flash with no documented way back.

## How the protocol works

```
 offset  size  field
 0       2     magic 0x2131
 2       2     total length (header + payload), big endian
 4       4     unknown (zero; 0xFFFFFFFF in hello)
 8       4     device id
 12      4     device stamp, seconds
 16      16    md5 checksum — holds the token while being computed

 checksum = md5(header[0..16] + token + encrypted_payload)
 key      = md5(token)
 iv       = md5(key + token)
 cipher   = AES-128-CBC, PKCS#7
 payload  = {"id":n,"method":"...","params":[...]}
```

Three details that cause most of the trouble:

- **The stamp must track the camera's clock.** The device rejects packets whose
  stamp has drifted. Both clients capture it at handshake and advance it
  locally; on a timeout they re-handshake rather than retrying blind.
- **Replies are matched by request id.** A UDP answer to a request that already
  timed out arrives late and lands on the next one. Both clients drop any reply
  whose `id` doesn't match.
- **crypto-js, not react-native-quick-crypto.** miIO needs MD5, which the faster
  library doesn't document support for. These packets are ~100 bytes, so pure
  JS costs nothing measurable.

## Custom firmware, if the probe comes up empty

[Xiaomi-Dafang-Hacks](https://github.com/EliasKotlyar/Xiaomi-Dafang-Hacks)
turns the camera into a plain HTTP/RTSP device: `rtsp://dafang:8554/unicast`, a
snapshot at `/cgi-bin/currentpic.cgi`, motor control at
`/cgi-bin/action.cgi?cmd=motor_up`, MQTT, SSH.

The catch: installation is an SD-card flash triggered at boot, and users on
`5.5.1.x` builds repeatedly reported the camera booting normally and ignoring
the card. `5.5.1_1025` is newer than any of those reports. **Assume it won't
take.** A failed attempt usually just boots stock; a failed *firmware downgrade*
is the part that bricks cameras — don't do that one.
